## 运行模式检测

本 skill 支持两种运行模式，通过 prompt 中的标记判断：

| 模式 | 检测方式 | 确认点行为 |
|------|---------|-----------|
| 非交互模式 | prompt 中包含 `[NON_INTERACTIVE]` 标记 | **所有确认检查点自动跳过**，直接执行后续步骤，最终产出物正常生成 |
| 交互模式 | prompt 中不包含 `[NON_INTERACTIVE]` 标记 | 按 agent.json 中 confirmations 配置的 mode 执行 |

**非交互模式下的特殊处理**：
- 所有需要用户确认的环节自动通过
- 问题清单正常写入分析报告文件，用户回答列留空
- 分析报告正常生成，在文档中标注"由 AI 自动生成，部分内容待确认"

---

## Purpose

将模糊需求想法转化为结构化的分析报告，完成"发散"工作——打开问题空间，梳理系统现状，识别候选方案方向，列出所有待确认问题。

本 skill 不做方案选定、不做功能架构设计、不生成 Baseline。

## 硬性边界

- 不生成 Baseline 文档（由 pm-baseline-gen 负责）
- 不生成 PRD 文档
- 不输出功能架构树（功能架构依赖选定方案，在 pm-baseline-gen 中方案选定后生成）
- 不做方案选定（由用户在分析报告基础上选择，在 pm-baseline-gen 中确认）
- 不写代码，不修改知识库
- 不要把"猜测"包装成"已确认信息"
- 不要向用户暴露原始 JSON
- 不要因为需求看起来简单就跳过分析
- 如果需求横跨多个彼此独立的顶层系统，在分析报告中建议拆分为多个子需求

## 输入

- 用户的需求描述（自然语言，可以很粗略）
- AI 知识库（按需读取，见 Phase 1.2 三层优先级策略）
- 已有的需求原稿（如有）

## 输出

`Developer/my-project/产品需求/{需求名}/{需求简称}-需求分析-v{N}.md`

每次重跑生成新版本文件（v1、v2...），版本号递增，不覆盖已有版本。

## 工作流程

### Phase 0：状态检查与中断恢复

扫描需求文件夹下已有产物，判断执行状态：

1. **扫描已有产物**：检查需求文件夹下是否存在分析报告文件（`{需求简称}-需求分析-v*.md`）和 Baseline 文件
2. **判断执行状态**：
   - 无任何产物 → 从 Phase 1 开始
   - 已有分析报告，问题清单"用户回答"列无内容 → 分析已完成但未回答，询问是否重跑（生成新版本）
   - **已有分析报告，问题清单"用户回答"列有内容（任意一条非空即算）→ 进入迭代分析模式（见 Phase 1-iter）**
   - **已有 vN 报告 + 有用户回答 + 无 vN+1 报告 → 迭代分析未完成（中断），询问是否继续**
   - 已有分析报告 + Baseline → 全流程已完成，询问用户意图
3. **向用户展示状态判断**（交互模式）/ **自动选择继续**（非交互模式：无产物→从 Phase 1 开始，有产物→自动判断路径）

### Phase 1：静默探索项目上下文（不需要用户参与）

#### 1.1 分析需求描述（先理解需求，再读知识库）

解读用户输入的需求描述，提取以下信息：

| 分析项 | 说明 | 用于指导知识库读取范围 |
|--------|------|---------------------|
| 核心功能目标 | 要做什么 | — |
| 涉及的业务域 | 属于哪个知识库子目录（ai-knowledge/xkf/xkf-xinde） | 决定读哪个子目录 |
| 涉及的服务列表 | 具体涉及哪些服务 | 决定读哪些服务的 docs |
| 涉及哪些角色 | 哪些角色使用该功能 | — |
| 核心数据对象 | 需要了解哪些表/实体 | 决定是否需要读 database-schema |
| 涉及的功能模块 | 修改/复用/新增哪些功能 | 决定是否需要读 business-domains |
| 是否涉及前端 | 是否需要了解页面结构 | 决定是否读 menu-tree/page-modules |
| 与现有系统的关联点 | 与哪些现有功能相关 | — |
| 涉及的前端页面与代码位置 | 对应哪些已有页面、前端组件代码仓库路径 | 决定读取 page-modules 与前端代码目录映射表 |
| 是否为接口类需求 | 是否以提供对内/对外接口、对接外部系统为核心目标 | 决定是否补充接口维度分析与知识库读取 |

#### 1.2 按需读取知识库（基于 1.1 分析结果决定读取范围）

根据 1.1 的分析结果，按以下**三层优先级**读取知识库信息：

```
优先级 1：已有分析报告中的「三、已确认的知识库信息」章节
  ↓ 信息不足时
优先级 2：需求目录下的「{需求简称}-知识上下文.md」文件（pm-conventions §10.4）
  ↓ 信息不足时
优先级 3：知识库原文件（按 pm-conventions §10.2 规则读取，范围由 1.1 分析结果限定）
```

**优先级 1 的适用场景**：Phase 0 检测到已有分析报告时，优先从报告的「三、已确认的知识库信息」章节获取已整理好的知识库摘要。

**"信息不足"判断规则**：

| 优先级层 | 判为"足够" | 判为"不足"需降级 |
|---------|-----------|-----------------|
| 已有分析报告 | 报告已覆盖 1.1 识别的所有服务和数据对象 | 1.1 识别出报告未覆盖的新服务或新数据对象 |
| 知识上下文文件 | 按 pm-conventions §10.4 现有规则判断 | 按 pm-conventions §10.4 现有规则判断 |

**关键约束**：
- 降级是"补读"不是"重读"——已从高优先级获取的信息不再重复读取
- 读取范围始终由 1.1 的分析结果限定，不做无目的的全量读取
- 无已有分析报告且无知识上下文文件时，直接走优先级 3

> 此三层优先级策略仅适用于本 skill。pm-conventions §10.4 的两层优先级规则（知识上下文文件 → 知识库原文件）仍是其他 skill 的默认行为。

**重要：知识库信息仅用于理解"系统现状"，不应将技术细节直接写入分析报告中的业务描述部分。**

**采集深度引导**：
对于需求明确涉及**修改/扩展**的数据表和功能模块，「已确认的知识库信息」章节应记录：
- 数据表的完整字段列表（不仅是"关键字段"）
- 现有功能的完整状态/流程定义（不仅是"涉及的部分"）
- 相关枚举的完整值列表

目的：为下游知识上下文文件提供充足的源数据，减少 pm-baseline-gen 阶段的补读。
对于需求仅"查询/引用"的表和功能，仍按现有规则只记录关键字段即可。

**读取重点**（当需要走优先级 3 时）：
- `project-overview.md`：了解角色体系和系统边界
- 需求涉及的服务目录下的 `business-domains.md` 和 `database-schema.md`
- 前端需求额外读取 `knowledge/docs/menu-tree.md`、`page-modules.md` 及**前端页面-代码路径映射表**，获取对应页面的组件代码仓库位置、核心文件路径
- 接口类需求额外读取对应服务的 `api-definitions.md`，获取现有接口清单、鉴权方式、字段规范与异常码定义

#### 1.3 识别模糊点与待确认问题

对比需求描述和知识库，找出所有需要澄清的**需求层面**问题。模糊点通常出现在：
- **范围不清**：用户说"管理 XX"，但没说包含增删改查中的哪些操作
- **角色不明**：没说谁来用这个功能，或者多个角色的权限边界不清
- **流程缺失**：描述了起点和终点，但中间的审核/审批/状态流转没提
- **数据关系模糊**：新增的数据对象和现有对象是什么关系
- **异常处理空白**：只说了正常流程，没提失败/取消/超时怎么办
- **与现有功能的关系**：知识库中有类似功能，是增强还是新建？
- **"保持一致"类模糊描述**：用户说"与 XX 功能保持一致"等，必须追问确认
- **影响范围**：功能改动了公共/通用逻辑，或出现"所有 XX"类表述时
- **隐私与数据安全**：涉及采集、存储、展示用户个人敏感信息（PII）时
- **接口类需求专属模糊点**：接口调用方、入参出参字段定义、异常码规范

**职责边界**：本步骤聚焦需求层面模糊点（范围、角色、流程、数据关系等），明确排除方案评估类问题（方案合理性/完整性/风险评估留给 Phase 1.4）。

#### 1.4 方案分析与设计

> 本 skill 评估方案的合理性并给出优化建议，但**不替用户做方案选定决策**。候选方案是 AI 基于评估给出的建议，最终选择权在用户。

检测用户输入中是否包含初步方案/解决思路：

**方案识别规则**：
- **算方案**：包含"怎么做/如何实现"层面的描述，如具体的功能设计、技术路径、流程改造方案
- **不算方案**：仅表达期望结果/目标（如"希望能关联工单""想要提升效率"），属于需求描述而非方案

**边界 case**：
- "需要一个列表页，包含工单号、客户名、状态字段，支持按状态筛选" → **不算方案**（描述了期望结果和功能点，未涉及怎么实现）
- "把工单关联关系存到 RecordRelation 表，通过 parent_id 字段做关联查询" → **算方案**（指定了具体的技术路径）
- "前半段是需求 + 后半段是方案" → **算方案**（包含实现层面描述，整体走方案评估）
- "需要一个关联查询功能，用弹窗形式展示" → **算方案**（有交互方案描述"弹窗形式"）
- "关联工单时，自动根据客户信息匹配推荐" → **算方案**（"自动匹配推荐"暗含算法/规则层面的实现思路）
- "希望客服能更快找到关联工单" → **不算方案**（仅表达目标/期望效果）
- 判断倾向：**宁可误判为有方案走评估（分支 A），不可漏掉方案走设计（分支 B）**

**误判退化机制**：走分支 A 后，如果评估结论为"用户输入不包含实质方案（仅为需求描述）"，则跳过评估表格输出，直接进入分支 B 的方案设计流程。在报告中标注"经评估，用户输入不包含实质方案，已转为设计模式"。

**分支 A：有初始方案 → 方案评估模式**

当用户输入中包含解决方案/设计思路/初步方案时，AI 必须先进行方案评估：

| 评估维度 | 说明 |
|---------|------|
| 完整性 | 是否覆盖了需求背景中的所有问题？有无遗漏场景？ |
| 合理性 | 提出的解法是否是该问题的最优/较优解？是否有过度设计或设计不足？ |
| 一致性 | 多个方案点之间是否有冲突或重复？ |
| 风险 | 方案可能带来的副作用、兼容性问题、运营风险 |

评估结论写入分析报告的「原始方案评估」章节，然后基于评估结果输出候选方案。

**分支 B：无初始方案 → 方案设计模式**

用户只提供了背景/问题描述，AI 基于问题分析和知识库现状，直接设计 1-3 个候选方案。

**两个分支的共同输出要求**：
- **候选方案必须是完整的、可直接进入 Baseline 的需求方案**，不是技术实现路径的变体
- 每个方案应覆盖所有功能点，而非只针对某个细节给变体
- 有初始方案时，候选方案是对原始方案的整合优化版本，如果原始方案不合理，可以给出完全不同的方案

#### 方案输出铁律

- 用户输入的任何方案/想法/设计，无论用词是"方案""设计""规划"还是其他，
  **一律视为待评估的输入素材**，不是已确认的需求（例外见下方）
- AI 必须先评估再输出候选方案，不可将用户方案原封不动作为候选方案
- 候选方案是完整的需求方案（覆盖所有功能点），不是实现路径变体

#### 接口类方案输出要求
- 若需求为接口类需求，候选方案必须明确：接口分类（对内/对外）、核心入参出参清单、异常处理机制
- 接口字段必须包含字段名、是否必填、业务含义、约束规则

#### 例外条件

- 当用户输入中包含**可追溯的确认表述**时，
  AI 应尊重该方案为已确认状态，**仅做风险提示**而非重新评估
- **可追溯的判定标准**：需包含**具体人/角色 + 具体事件**。
  - ✅ 可追溯示例："已与后端 lead 确认定稿"、"经产品评审会通过的方案"、"XX 总监审批的设计"
  - ❌ 不可追溯示例："已确认"、"这是最终方案"、"讨论过了"、"看过了"
- 不可追溯表述不触发例外，仍按待评估处理
- 触发例外时，报告中标注"用户标注为已确认方案（来源：{用户表述}），以下为风险提示"

#### 1.5 L1 代码逻辑验证（条件触发）

**触发条件**：方案涉及复用或修改已有功能时。纯新增功能不需要。

读取知识库中的业务层文档，确认功能的存在性和基本逻辑流程。验证结论写入分析报告的"已确认的知识库信息"章节。

**粒度约束**：L1 验证结论只描述功能的存在性和方案一致性判断，不写具体实现逻辑。

#### 1.6 复杂度判断

按 pm-conventions §9.1 规则判断需求复杂度（简单/复杂），结论写入分析报告头部。

### Phase 3：一次性输出完整分析报告

将分析报告写入文件，同时在对话中展示核心内容。

#### 分析报告内容要求

按 `templates/analysis-report.md` 模板结构输出，需包含：

1. **原始需求**：用户输入的原始内容，直接添加不加工
2. **建议需求命名与模块归属**：基于分析给出建议，作为问题清单首项确认
3. **已确认的知识库信息**：从知识库中提取的与需求相关的现状信息（涉及哪些服务、现有数据结构、现有功能逻辑、L1 验证结论）
  - 前端页面与代码位置：涉及的已有页面名称、页面对应的前端代码仓库路径、核心组件文件相对路径（仅涉及前端需求需包含）
  - 现有接口现状：涉及的已有接口清单、接口定义、鉴权方式、核心字段规范（仅接口类需求需包含）
4. **原始方案评估**（条件章节）：仅当用户输入包含初步方案时生成，按完整性/合理性/一致性/风险四维度评估
5. **候选方案**：基于分析（和评估，如有）后给出的完整需求方案
   - 每个方案覆盖所有功能点，可直接作为 Baseline 生成的输入
   - 有初始方案时，候选方案是对原始方案的整合优化版本
6. **待确认问题清单**：分层组织（详见模板）

#### 问题清单编制规则

1. 需要用户回答的问题，**全部列出**，不同候选方案如果有不同的确认问题也需覆盖
2. **分层展示**：
   - 🔴 必答问题（阻塞级，按 pm-conventions §4 定义）：缺失会导致开发无法开工
   - 🟡 建议确认（有默认值/倾向性结论）：不确认也能推进，但可能产生理解偏差
3. **先列通用问题，再按方案分列差异问题**，避免把方案和问题混在一起
4. **级联问题「摊平」为条件化清单**：不要嵌套"如果你选 A 再回答这个"，而是写成"[条件：选择方案 A 时] 具体问题"
5. 问题清单末尾增加兜底提示

#### AI 建议列编制规则

1. **对于 AI 有足够信息判断的问题**：给出推荐答案 + 简要理由
   - 示例：`建议选方案A。理由：改动面小，现有 RecordRelation 表可复用，风险可控`
2. **对于 AI 无法判断的问题**：标注"需业务侧确认"+ 说明为什么 AI 无法判断
   - 使用条件：必须先读取相关服务的 `business-domains.md` 和 `database-schema.md` 进行分析，仅在知识库中确实无相关信息**且**问题涉及业务策略/运营偏好时才可使用
   - 禁止将"需业务侧确认"作为规避分析的兜底手段
   - 示例：`需业务侧确认。已查 {服务名}/docs/business-domains.md 和 database-schema.md，无相关配置，此问题涉及运营策略偏好，非技术问题`
3. **对于用户原始方案中已提出的疑问**：AI 必须先读取相关服务的 `business-domains.md` 和 `database-schema.md` 后给出分析建议，不能直接转成"待确认问题"了事
   - 示例：用户写"补件请求触发是否有这个功能？" → AI 应查知识库后回答"知识库中未找到相关功能，大概率不存在。建议本期仅支持手动设置"

#### 输出后行为

1. 告知用户分析报告文件位置
2. **交互模式**：引导用户回答问题清单（可直接在对话中回答，也可在分析报告文件的"用户回答"列中填写）
3. **非交互模式**：问题清单写入分析报告文件，用户回答列留空，直接输出分析报告并终止流程
4. 如果用户在对话中回答了问题，将回答回填到分析报告文件的"用户回答"列中，确保跨会话可追溯
5. 建议用户回答完成后调用 `pm-baseline-gen` 生成 Baseline

### 流程结束声明

> 详见 pm-conventions §11。分析报告输出后流程终止。
> 追加会话切换强引导（按 pm-conventions §11.4），引导执行 `/pm-baseline-gen`，附带需求名和分析报告路径。
> 会话切换引导中需增加前置条件提示：
>
> ```
> > 📋 下一步操作提示（复制到新会话中使用）：
> > ⚠️ 请先在分析报告文件中填写"用户回答"列，然后执行：
> > /pm-baseline-gen {需求名} {分析报告路径}
> ```
