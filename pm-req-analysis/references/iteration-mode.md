# 迭代分析模式

> 来源：pm-req-analysis Phase 1-iter
> 触发条件：当上一版分析报告有用户回答时触发

## 1-iter.1 读取上一版报告及用户回答

从上一版分析报告的问题清单中提取所有用户回答。

## 1-iter.2 用户回答意图分类

对每条用户回答进行意图分类：

| 意图类型 | 识别特征 | 处理方式 |
|---------|---------|---------|
| ✅ 已确认 | 直接给出明确答案，如"选方案A"、"是"、"不需要"、"仅投诉类型" | 纳入已确认信息，用于方案细化 |
| ❓ 求建议 | 反问句式、表达不确定，如"这个功能存在吗？"、"你建议呢？"、"不确定怎么选" | AI 必须给出分析建议和推荐，在新版报告中补充 AI 分析 |
| ⚠️ 有条件确认 | 给了答案但附带条件/疑虑，如"暂时选A，但如果XX的话可能要改" | 记录确认答案 + 标注条件，条件本身可能产生新的待确认问题 |
| ⏳ 未回答 | 留空或标注"待定" | 保持待确认状态 |
| ➕ 新增需求 | 回答中附带了原始需求未提及的新功能描述，如"选方案A，另外还需要一个导出功能" | 拆分为：原问题的确认回答 + 新增需求点。新增需求点纳入新版报告的分析范围，可能产生新的候选方案调整和待确认问题 |

**边界 case 示例**：
- "A吧，不过我不太确定" → ⚠️ 有条件确认（给了答案但表达不确定）
- "这个功能现在有吗？如果有就复用，没有就新建" → ⚠️ 有条件确认（条件取决于系统现状，AI 需查知识库后判断走哪个分支）
- "都行，你定" → ❓ 求建议（表面像确认，实际是把决策权交给 AI）
- "选方案A，另外还需要一个导出功能" → ✅ 已确认（选方案A）+ ➕ 新增需求（导出功能）

**兜底规则**：无法判断意图时，默认归类为"求建议"（宁可多给建议，不可误标已确认）。

**分类依据标注**：迭代报告中每条回答的意图分类结果必须标注分类依据，格式为"分类：{意图类型}（依据：{判断理由}）"。示例：
- "分类：❓ 求建议（依据：句式含反问词'吗'，未给明确答案）"
- "分类：✅ 已确认（依据：直接给出选择'方案A'）"
- "分类：❓ 求建议（依据：兜底规则，无法判断意图）"

**"未回答"判断规则**：用户回答列为空、仅含空格、或仅含占位符（如"-"、"/"、"—"）均视为未回答。

**用户回答与 AI 建议不一致时的处理**：
- AI 应尊重用户决策，不反复劝说
- 如果用户否决的 AI 建议涉及风险（如兼容性、数据一致性），在方案决策摘要中增加"风险提示"标注
- 如果用户否决的 AI 建议仅涉及偏好（如交互方式、命名风格），直接采纳用户决策，不标注

## 1-iter.3 基于新信息重新分析

**知识库补读判断**（在重新分析前执行）：
- 检查用户回答是否引入了新的业务域、服务或数据对象（如新增需求涉及新服务）
- 如果有新增 → 检查已有分析报告「三、已确认的知识库信息」是否已覆盖
  - 已覆盖 → 不重复读取
  - 未覆盖 → 按 Phase 1.2 的三层优先级补读（已有报告 → 知识上下文文件 → 知识库原文件）
- 如果没有新增 → 沿用已有报告中的知识库信息，不触发补读

**重新分析**：
- 已确认信息可能缩小了方案空间 → 重新评估候选方案（**沿用 Phase 1.4 的评估维度：完整性/合理性/一致性/风险**，确保 v1 与迭代版评估标准一致）
- 求建议类回答 → AI 基于知识库和分析给出建议
- 有条件确认 → 拆解条件，识别新的待确认问题
- 前一版的问题可能因新信息变得不相关 → 清理过时问题

## 1-iter.4 生成方案决策摘要

当满足以下最低门槛时生成「方案决策摘要」章节：
- 已选定候选方案（Q-02 或等价问题已确认回答）
- 所有🔴必答问题已确认回答

如条件未满足，不生成此章节。

## 1-iter.5 输出新版本报告

版本号递增（v2/v3...），包含完整的重新分析结果，不是在上一版基础上简单标注。
