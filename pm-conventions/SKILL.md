## 运行模式检测

本 skill 支持两种运行模式，通过 prompt 中的标记判断：

| 模式 | 检测方式 | 确认点行为 |
|------|---------|-----------|
| 非交互模式 | prompt 中包含 `[NON_INTERACTIVE]` 标记 | 自动识别查询范围，直接输出约定内容 |
| 交互模式 | prompt 中不包含 `[NON_INTERACTIVE]` 标记 | 按 agent.json 中 confirmations 配置的 mode 执行 |

**注意**：pm-conventions 为纯参考文档型 skill，无交互确认点，两种模式下行为一致。

---

## Purpose

PM skill 体系的"宪法"——集中定义所有 PM skill 共享的约定。各 PM skill 引用本 skill，不各自定义。

## 2. 产品需求目录规范

### 项目根目录判断

1. 当前工作目录下存在 sources/ → 当前目录即为项目根目录
2. 存在 prd-knowledge/ 或 coding-knowledge/ → 当前目录即为项目根目录
3. 否则 → 使用当前工作目录

每个需求在 `Developer/my-project/产品需求/` 下拥有独立目录：

```
Developer/my-project/产品需求/{需求名}/
├── {需求简称}-Baseline.md                    # Baseline 文档（唯一一份，原地更新）
├── {需求简称}-知识上下文.md                    # 本需求相关的知识库信息摘要（由 pm-baseline-gen 生成，后续 skill 按需追加）
├── 变更记录/                                  # Baseline 更新详情（独立文件，AI 无需读取）
│   ├── baseline-v1.md
│   ├── baseline-v2.md
│   └── ...
├── 需求文档/
│   ├── {需求简称}-需求文档-v1.md
│   └── ...
├── 修改建议/
│   └── {需求标题}-修改建议-v1.md
├── 评审报告/
│   └── {需求标题}-v1-需求评审报告.md
├── 原型/
│   └── ...
├── 操作指引/
│   └── {操作指引名称}.md
├── sessions/
│   └── {request_id}/
│       ├── update_change_list.json
│       ├── update_confirmed_sections.json
│       └── update_confirmation_log.md
└── {需求名}-变更执行清单-{日期}.md            # 仅中断时保存
```

## 3. 文档版本管理规则

### 3.1 各文档类型的版本策略

| 文档类型 | 版本策略 |
|---------|---------|
| Baseline | 单文件原地更新，通过内部"版本记录"追踪 |
| 需求文档（PRD） | 新建文件，版本号递增，禁止修改已有版本 |
| 修改建议 | 新建文件，版本号递增 |
| 评审报告 | 同一 PRD 版本重复评审时可覆盖 |
| 原型（HTML） | 重新生成时可覆盖 |
| 操作指引 | 单文件原地更新 |
| 知识上下文 | 单文件追加更新，通过文件头部更新时间追踪最新状态 |

### 3.2 禁止操作 [必须]

- **禁止删除**已生成的需求文档、修改建议等历史版本文件
- **禁止原地修改**已有的需求文档文件（应创建新版本文件）
- **禁止清空**需求文件夹下的已有产物

### 3.3 Baseline 文档更新操作规则

> 详细规则见 `references/baseline-update-rules.md`，涉及 Baseline 更新的 skill（baseline-gen/prd-update/prd-review）执行前读取。

## 4. 问题分级标准

| 级别 | 定义 | 判断标准 |
|------|------|----------|
| 🔴 阻塞 | 缺失关键信息，开发无法开工 | 开发会说"这块怎么做？我得找 PM 确认" |
| 🟡 建议 | 信息不够完善，开发能做但容易理解偏差 | 开发会说"大概知道怎么做，但细节不太确定" |
| 🔵 提示 | 可以更好，但不影响开发理解和执行 | 开发不会有疑惑 |

## 5. 文档引用与会话隔离规则

### 5.1 文件读取铁律 [必须]

- 执行任何步骤时，必须从用户指定的文件路径重新读取文件内容
- 禁止使用本会话中此前生成、讨论或缓存的文档版本
- 文件内容与对话内容不一致时，以文件为准并向用户确认差异

### 5.2 中断恢复规则

skill 触发时扫描需求文件夹下已有产物，判断执行状态，向用户展示并提供选择（继续/重新开始/指定环节）。"重新开始"不等于"清空"，历史版本文件必须保留。

### 5.3 变更执行清单持久化规则

- 正常完成：不持久化，结果在会话中输出
- 执行中断：自动保存为 `{需求名}-变更执行清单-{日期}.md`
- 恢复执行：检测到未完成清单时提示用户

### 5.4 Phase 0 自动执行规范

适用于 pm-prd-draft 和 pm-prd-update 的 Phase 0 状态检查：

- **默认自动执行**：AI 自动判断执行状态并直接进入对应路径，仅在异常情况下暂停询问
- **状态通知**：自动执行后输出一行状态摘要（如 `✅ 已检测到 Baseline v3，无已有需求文档，从 Phase 1 开始`）
- **失败回退**：自动检测失败时回退到手动确认模式（展示检测结果供用户选择），不中断流程

## 6. 文档格式规范（全局统一）

### 6.1 输出格式

- 需求文档用 Markdown 输出，不要 HTML/纯文本/JSON（颜色标记 `<font>` 标签除外）
- 表格用 Markdown 表格，流程图用 Mermaid 语法

### 6.2 标题层级与编号规则 [必须]

- 不设独立的文档标题行
- `#` 一级章节（中文数字编号：`# 一、需求背景`）
- `##` 二级章节（阿拉伯数字：`## 3.1 分配规则增强`）
- `###` 三级章节（`### 3.1.1 通用能力`）
- `####` 四级章节（仅在三级内容较多时使用）
- 功能清单按模块粒度组织，不带功能编号

### 6.3 Mermaid 语法规范

> 语法规则与模板见 `templates/mermaid-templates.md`，生成流程图时读取。

### 6.4 颜色编码

| 颜色 | 用途 | 标签 |
|------|------|------|
| 红色 `#cc0000` | 核心逻辑/易混淆规则 | 影响核心流程走向的规则；在需求文档中，baseline中的规则均为核心逻辑； |
| 橙色 `#ff9900` | 待确认逻辑 | Baseline 中 Q-xx 在正文中的引用 |
| 灰色 `#cccccc` | 非本期但需预留 | 与本期有技术关联的后期功能；保留作参考的现有逻辑 |

灰色处理两步：
1. 判断是否保留：与本期有技术关联 → 保留标灰；无关联 → 从文档中删除
2. 标灰的作用：告诉读者"不是本期开发范围，但对理解本期需求有参考价值"

### 6.5 文件命名规范

| 术语 | 定义 | 用途 |
|------|------|------|
| 需求标题 | 需求的完整名称 | 修改建议、评审报告的文件名 |
| 需求简称 | 文件名友好的缩短版 | Baseline、需求文档的文件名 |

两者均在 pm-req-analysis 分析阶段与用户确认。

**需求简称的计算规则（硬约束，校验端与生成端必须一致）**：

```
需求简称 = 需求目录名去除连字符 `-`、空格 ` `、下划线 `_` 后的字符串
```

| 需求目录名 | 需求简称 |
|-----------|---------|
| `V43-智能质检` | `V43智能质检` |
| `V42-1 自动停复催` | `V421自动停复催` |
| `V42_测试` | `V42测试` |

> ⚠️ 此规则由 skill_agent 的 `skill_postprocess.normalize_req_short()` 实现并作为单一真相源。各 skill 在 SKILL.md 中告诉 AI 的命名规则必须与此一致，否则会导致产出校验失败。

| 文档 | 文件名格式 |
|------|-----------|
| 需求文档 | `{需求简称}-需求文档-v{N}.md` |
| 修改建议 | `{需求标题}-修改建议-v{N}.md` |
| 评审报告 | `{需求标题}-v{N}-需求评审报告.md` |
| Baseline | `{需求简称}-Baseline.md` |

### 6.6 有序列表规范

凡是用 1. 2. 3. 编号的列表，每个编号必须换行，严禁将多个编号挤在同一行。

## 11. 流程交付与 Skill 切换规则

### 11.1 流程终止判定

同时满足以下两个条件时，skill 流程视为**终止**：
1. 最终交付物文件已写入磁盘
2. 已向用户输出总结

### 11.2 终止后行为约束

1. **禁止编辑已交付文件** — 必须重新进行 skill 触发词匹配
2. **流程衔接示例**：review 完成后用户说"改需求" → 应触发 pm-prd-update，而非继续 review；pm-prd-update 完成后用户说"还要改一处" → 应触发 pm-prd-update 新一轮 Phase 1；pm-proto-review 完成后用户说"写 PRD" → 应触发 pm-prd-draft；pm-proto-review 完成后用户说"再评审一轮" → 应触发 pm-proto-review 新一轮

### 11.3 禁止在会话中重复确认报告中的问题

Skill 产出的问题清单（如分析报告中的待确认问题）直接写入文件，引导用户在文件中填写回答。**禁止**用 AskUserQuestion 在会话中逐条确认已列入报告的问题，这会产生不必要的交互轮次和 token 消耗。

### 11.4 流程中途退出

用户在执行中发出其他 skill 触发词时：告知当前进度 → 询问中断/完成后切换/取消 → 中断时记录状态到 sessions

### 11.5 会话隔离与模型使用规则

> 详细规则（各 skill 会话策略、模型分配、后续引导格式）见 `references/session-isolation.md`。

## 12. 术语定义

| 术语 | 定义 | 适用场景 |
|------|------|---------|
| 探索性原型 | 基于 Baseline 生成的原型，精度约 80%（核心字段完整、辅助字段可能缺失），用于交互方案验证 | pm-proto-gen Baseline 模式产出、pm-proto-review 输入 |
| 精确原型 | 基于 PRD 生成的原型，精度约 95%（字段、规则、状态完全对齐 PRD），用于开发参考 | pm-proto-gen PRD 模式产出 |
| 知识上下文文件 | 需求目录下的 `{需求简称}-知识上下文.md`，由 pm-baseline-gen 从分析报告「已确认的知识库信息」章节提取生成，后续 skill 按需追加 | pm-conventions §10.4 |
| PRD / 需求文档 / 需求定稿 | 三者等价，均指交付给开发团队的完整需求文档。各 skill 正文中统一使用"需求文档"，触发词保留多个别名以兼容用户习惯 | 全局 |
| 方案决策摘要 | 分析报告迭代版本（v2+）中的「方案决策摘要」章节，当已选定候选方案且所有🔴必答问题已确认回答时生成。是 pm-baseline-gen 的直接输入（权威来源），优先级高于「候选方案」和「原始需求」章节 | pm-req-analysis → pm-baseline-gen 接口 |
| 阶段 | PM 流程中的最小执行单元，独立 skill 体系中对应一个独立的 PM skill | 全局 |
| 接口类需求 | 以提供对内/对外数据接口、对接外部系统为核心目标的需求，核心产出为接口定义与对接规则 | 全局 |
| 前端代码位置映射 | 业务页面对应的前端代码仓库路径、组件文件位置，用于原型生成与前端开发参考 | pm-req-analysis / pm-baseline-gen |

## 14. 文件缺失降级策略

所有 skill 执行时，如果依赖的输入文件不存在，按以下统一策略降级处理，而非中断执行：

| 缺失文件 | 影响 | 降级策略 |
|----------|------|---------|
| `coding-knowledge/` | 技术分析精度下降 | 从"定位"降级为"推测"，继续执行但在产出物中标注"未使用编码知识库，信息精度可能不足" |
| `prd-knowledge/` | 业务上下文不完整 | 跳过知识库交叉校验，仅做文档自身完整性检查 |
| Baseline 文档 | 无法执行一致性校验 | 跳过 Baseline 相关检查，在报告中标注"未找到 Baseline 文件" |
| 原型文件 | 缺少可视化参考 | 仅依赖 PRD 文字描述 |

**核心原则**：缺少输入文件时，skill 应明确告知用户精度下降的影响，但仍基于可用输入继续执行。只有在核心输入完全缺失（如 pm-prd-draft 缺少 Baseline）时才中断并引导用户补充。

## 15. Skill 分层与调用规则

```
约定层: pm-conventions
PM层:   pm-baseline-gen, pm-prd-draft, pm-prd-review, pm-prd-update,
        pm-proto-gen, pm-proto-review, pm-baseline-mapping, pm-operation-guide
工具层: sync-repos, tool-tapd, testability-api-client
```

调用方向：上层可调用下层，同层可互相调用，下层不可调用上层。

**基准 Skill 规则**：

| 领域 | 基准 Skill | 规则 |
|------|-----------|------|
| 代码仓库管理 | sync-repos | 所有代码克隆/分支/同步操作统一由 sync-repos 执行。其他 skill 只读取已存在的本地仓库，不自行 clone |
| 可测性分析 | testability-api-client | 所有可测性分析统一通过 API 调用 |
| TAPD 操作 | tool-tapd | 所有 TAPD API 调用统一使用 tool-tapd 的脚本 |
