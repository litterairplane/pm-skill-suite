## 运行模式检测

本 skill 支持两种运行模式，通过 prompt 中的标记判断：

| 模式 | 检测方式 | 确认点行为 |
|------|---------|-----------|
| 非交互模式 | prompt 中包含 `[NON_INTERACTIVE]` 标记 | **所有确认检查点自动跳过**，直接执行后续步骤，最终产出物正常生成 |
| 交互模式 | prompt 中不包含 `[NON_INTERACTIVE]` 标记 | 按 agent.json 中 confirmations 配置的 mode 执行：`auto_pass`=自动通过，`user`=根据 agent.json 确认点模式执行 |

**非交互模式下的特殊处理**：
- 所有需要用户确认的环节（方案确认、架构确认、内容确认等）一律自动通过
- 待确认问题写入对应文件，标记为"待确认（非交互模式）"
- 最终产出物正常生成，在文档中标注"由 AI 自动生成，部分内容待确认"

## Purpose

基于 pm-req-analysis 输出的分析报告和用户的问题回答，完成"收敛"工作——确认方案、补全细节、生成 Baseline 文档。

本 skill 重点在于：根据已知信息做方案确认、功能架构设计、细节补全，最终输出可交给 pm-prd-draft 的 Baseline 文档。

## 硬性边界

- 不撰写 PRD 文档（由 pm-prd-draft 负责）
- 不写代码，不修改知识库
- 不要把"猜测"包装成"已确认需求"
- 不要向用户暴露原始 JSON
- 发现 3 个以上 🔴 阻塞级新问题时（按 pm-conventions §4 标准判定），**提示用户重跑 pm-req-analysis**，不在本 skill 里大量补充分析
- 无分析报告时引导用户先运行 pm-req-analysis，不可跳过
- 功能架构必须基于用户选定的方案生成，不输出未选定方案的架构
- 知识库信息可能滞后于最新代码，涉及具体实现细节时需注意时效性；用户需求若要改变现有逻辑不应质疑
- 不得遗漏分析报告中已确认的任何需求细节，所有已确认结论、字段定义、约束规则必须完整落地到 Baseline 文档
- 需要新增接口类需求必须在【业务需求】中体现，并完整记录接口定义、字段、对接规则，不得因使用产品语言省略技术对接核心细节

## 执行指导

- 不要因为任务看起来简单就跳过方案确认和功能架构设计
- 不要等到信息绝对完美才给出当前确认版本
- 把已确认的范围、假设、约束、选定方案信息记录到 Baseline 文档中
- 功能架构一旦确认，后续更新 Baseline 时需同步维护

## 输入契约

本 skill 的输入来自两个来源：

1. **分析报告文件**：`产品需求/{需求名}/{需求简称}-需求分析-v{N}.md`（由 pm-req-analysis 生成）
2. **用户的问题回答**：用户在对话中提供的对分析报告待确认问题清单的回答

**必须**：Phase 1 开始时，从文件路径读取最新版本的分析报告文件（遵循 pm-conventions §5.1 文件读取铁律），不使用对话缓存。

## 输出

- `Developer/my-project/产品需求/{需求名}/{需求简称}-Baseline.md`
- `Developer/my-project/产品需求/{需求名}/{需求简称}-知识上下文.md`

Baseline 仅维护一份文件，版本号通过文档内部"版本记录"追踪，文件名不含版本号。
知识上下文文件由 Phase 3 在生成 Baseline 的同时输出，内容提取自分析报告「已确认的知识库信息」章节，并整合 Phase 1-2 中从知识库补充验证的信息。

## 工作流程

### Phase 0：状态检查与中断恢复

按 pm-conventions §5.2 规则，扫描需求文件夹下已有产物，判断执行状态：

1. **扫描已有产物**：检查需求文件夹下是否存在分析报告和 Baseline 文件
2. **判断执行状态**：
   - 有分析报告但无 Baseline → 正常路径，从 Phase 1 开始
   - 有分析报告 + 已有 Baseline → **忽略已有 Baseline 内容**，从分析报告重新读取全部信息，完整执行 Phase 1 → 2 → 3，在 Phase 3 中重新生成 Baseline 文件（覆盖已有文件并递增版本号）
   - 有分析报告 + 已有 Baseline + **无知识上下文文件** → 按上一条执行，Phase 3 同时补充生成知识上下文文件
   - 无分析报告 → 提示用户先运行 pm-req-analysis
3. **向用户展示状态判断**（交互模式）/ **静默执行**（非交互模式）：告知用户检测到的产物状态和即将执行的路径，直接进入 Phase 1（无需额外确认）

**⚠️ 禁止行为**：检测到已有 Baseline 时，**不得**将流程简化为"对比验证已有 Baseline 是否覆盖分析报告"。必须完整执行 Phase 1（读取分析报告）→ Phase 2（交互确认）→ Phase 3（重新生成文件），不可跳过任何 Phase。

---

### Phase 1：读取输入与差异识别

#### 1.1 读取分析报告

从文件路径读取最新版本的分析报告，提取以下信息：
- 原始需求
- 已确认的知识库信息
- 候选方案方向
- 待确认问题清单（含清单中所有已确认信息，以及清单未提及单独补充信息）
- 复杂度判断

#### 分析报告读取优先级

读取需求分析报告时，按以下优先级确定方案依据：
1. 「方案决策摘要」章节 → 作为 Baseline 的直接输入（权威来源）
2. 如果没有「方案决策摘要」→ 按 Phase 1.2 现有逻辑处理（读取「候选方案」+「待确认问题清单」章节，引导用户选择方案）
3. 「原始需求」章节 → 仅用于理解需求背景和问题域，不作为方案依据
4. 「原始方案评估」章节 → 仅用于理解方案演变过程，不作为方案依据

#### 分析报告版本规则

始终读取最新版本的分析报告（按版本号排序）。旧版本报告仅供追溯，不作为输入。

#### 1.2 读取用户回答

优先从分析报告文件的问题清单"用户回答"列读取用户回答；如"用户回答"列为空，则从对话中获取。整理为结构化的确认结论：
- 需求命名与模块归属（确认或修改）
- 选定方案
- 各问题的回答

**方案未选定处理**：如果用户未在回答中明确选择方案，先引导用户完成方案选择再继续后续环节。方案选择是功能架构设计的前提，不可跳过。

**回答解析规则**：用户回答中可能包含条件性同意或嵌入式反提议，必须识别并拆分处理：
- 当回答包含转折信号词（"但"、"不过"、"有个问题"、"是否可以"）时，将转折后的内容提取为**新的追问项**，在 Phase 2 中处理
- 不可将用户的反提议/质疑默认视为"已确认"而忽略——用户选择了某个选项但附带了替代方案建议时，该建议必须在 Phase 2 中正式追问并给出分析后再确认
- 示例：用户回答"选项A，但有个问题：是否可以不用子状态直接新增挂起状态？" → 确认项="选项A"，新追问项="是否可以不用子状态直接新增挂起状态"

#### 1.3 识别新增待确认信息

基于用户回答，识别是否产生新的待确认问题：
- 用户回答引发的级联问题
- 选定方案带来的新确认需求
- 用户回答与知识库信息的不一致点

**允许按需局部读取知识库**（引用 pm-conventions §10），用于验证用户回答与系统现状的一致性。不需要全量重读。

#### 1.4 阻塞级问题检查

统计新发现的 🔴 阻塞级问题数量（按 pm-conventions §4 标准）：
- **≤ 2 个新阻塞问题**：在 Phase 2 中追问解决
- **≥ 3 个新阻塞问题**：暂停并提示用户重跑 pm-req-analysis，说明原因

#### 1.5 输出当前理解

向用户展示：
- 已确认的核心信息摘要
- 新发现的待确认问题（如有）
- 阻塞检查结论

---

### Phase 2：交互确认与方案收敛（2 轮）

#### 第一轮：综合确认（追问 + 风险 + 数据指标）

按维度分区输出以下三部分内容，每个区域用 `---` 和**加粗标题**明确分隔，三个区域的内容互相独立。用户可逐区确认或标注需修改部分（未标注的视为通过）：

---
**追问结论**

如果 Phase 1 识别到新的待确认问题，输出追问结论：
- Phase 1 识别的新增待确认问题及建议答案
- 详细变更点补充（变更的页面/模块/流程、变更前后行为、涉及的字段/状态/规则、新增字段的定义、流程修改的细节等）
- 默认假设确认

---
**风险评估**

在方案确定后，主动判断以下维度，如涉及则列出：
- 权限管理
- 灰度发布
- 旧数据处理/已有功能兼容
- 数据验证

**处理方式**：涉及的内容在 Baseline 中合并为一个「上线风险与兼容性」章节；不涉及的，Baseline 和后续需求文档中均不体现。

---
**数据指标**

**前置判断**：AI 先根据需求内容判断是否涉及数据指标（新增/修改数据表字段、需要效果度量等）。如不涉及，一句话告知用户"本需求不涉及数据指标需求"并跳过。

如涉及，输出：

📊 **数据指标建议**

| 维度 | AI 建议 |
|------|--------|
| 数据同步 | {是否涉及 + 具体表/字段} |
| 效果验证指标 | {建议指标 + 计算方式} |
| 统计维度拆分 | {维度列表} |
| 交付路径推荐 | {观远报表 / AI 统计工具短期观察 / 均不需要} |

**结论及后续处理**：

| 结论 | Baseline 写法 | PRD 体现 |
|------|-------------|---------|
| 仅需数据同步，无指标需求 | 在对应功能模块核心规则中标注数据同步要求（含具体表/关键字段） | 对应功能模块的业务规则中注明 |
| 需要数据指标 — 观远报表 | 新增独立模块记录统计方式、维度、口径；标注交付方式为"观远报表"，存在大数据团队排期依赖 | 需求详情中作为独立功能模块 |
| 需要数据指标 — AI 统计工具短期观察 | 新增独立模块记录统计方式、维度、口径；标注交付方式为"AI 统计工具短期观察" | 需求详情中作为独立功能模块 |
| 均不需要 | 不体现 | 不体现 |

> 看板/报表的前端配置由产品自行完成，不在需求文档中体现。两条路径下，开发均需在开发周期内提供统计口径、功能上线后提供验证数据。

> 用户可以逐区回复，如"追问部分确认，风险部分有修改，数据指标确认"，不要求一次性全部确认。

#### 第二轮：功能架构确认

功能架构是后续所有 skill 的工作基础，必须在此环节确保准确。

基于选定方案和复杂度判断结论（来自分析报告），输出功能架构：

- **简单需求**：可省略通用能力层和能力引用矩阵，直接按业务场景列出功能
- **复杂需求**：输出完整的通用能力层 + 业务场景层 + 能力引用矩阵

**功能架构树格式**：
```
功能架构
├── 通用能力层（如有）
│   ├── [能力1]：一句话描述
│   └── [能力2]：一句话描述
└── 业务场景层
    ├── [场景1]
    │   ├── [功能A]：一句话描述
    │   └── [功能B]：一句话描述（引用 能力1）
    └── [场景2]
        └── ...
```

**能力引用矩阵**（可选，仅存在通用能力时输出）：格式见 pm-conventions §1.3。

**约束**：
- 通用能力判定标准：被 2+ 业务场景引用的功能逻辑
- 仅被 1 个场景使用但具有明显独立性的功能也可提为通用能力（需与用户确认）

**确认检查点**：
- **交互模式**：功能架构输出后，**根据 agent.json 确认点模式执行**，确认通过后再进入确认总结。
- **非交互模式**：自动通过，直接进入确认总结。

**架构一致性校验**：输出功能架构前，执行以下校验：
- **引用归属一致性**：同一通用能力的多个引用方，如果业务语义相近（如跟进同步/完结同步/挂起同步都引用操作同步机制），应归属于同一业务场景分组，或在不同分组中明确说明归属差异的原因
- **如发现不一致**：在功能架构输出时向用户说明归属决策理由，由用户确认

#### 确认结束时的总结

所有确认完成后，输出理解摘要供用户最终确认：

```
📋 **理解摘要**（请确认以下理解是否准确）

**需求全貌：**
- 需求名称：{名称}
- 所属模块：{模块}
- 涉及系统：{系统列表}
- 涉及角色：{角色列表}

**各功能模块理解：**

| 功能模块 | AI 理解 | 状态 |
|---------|---------|------|
| F-01 {功能名} | {一句话描述} | 已确认 / 待确认 |

**已确认的设计决策：** {要点列表}
**优化建议（已确认采纳）：** {建议列表}
**待确认（需要后续补充）：** {待确认项}

确认无误后，我来生成 Baseline 文档。（非交互模式下自动通过，直接生成 Baseline）
```

### Phase 3：Baseline 生成与确认

将分析报告的已确认内容和 Phase 1-2 交互确认的结果进行整合，输出 **Baseline 文档**。

#### 输出路径

`Developer/my-project/产品需求/{需求名}/{需求简称}-Baseline.md`

仅维护一份文件，所有后续更新在原文件上直接修改。

#### Baseline 文档规范

- **核心规则粒度**：Baseline 记录所有已确认的核心规则与约束细节，包括字段定义、状态流转、接口规范、边界条件等，不得省略分析报告中已确认的任何结论；未确认过的功能详细交互、页面级描述由 PRD 初稿补充展开；
- **融合而非追加**：需要结合本次内容与原始需求，生成一份新的完整 Baseline
- **记录版本**：每次更新 Baseline 都需要记录版本和变更摘要
- **文档结构**：文档分为"版本记录"、"确认结论内容（概述→术语→架构→核心规则→风险）"、"待确认项"、"需求文档位置映射"四个区域
- **改写约束**：pm-baseline-gen 自身执行时（无论首次生成还是重新生成）均可写入/覆盖 Baseline 文件；其他 skill 仅在用户明确要求"修改/更新 Baseline"环节可改写 Baseline，其余环节以 Baseline 为判断基准
- **编号规则**：C-XX 编号按 Baseline 文档结构顺序从 C-01 开始连续分配，不沿用分析报告中的确认结论 ID。第五章模块核心规则中的**每条规则都必须有 C-XX 编号**，不得遗漏。数据指标部分使用 C-DS-XX 独立序列。映射表中的编号与正文保持一致
- **排除规则**：已确认"本需求不做"或"已排除"的功能点，**不写入第五章模块核心规则**。如需记录排除决策，在「待确认项」下方新增「已排除项」小节，简要说明排除原因（如"已有其他需求覆盖"）
- **转写规则**：将确认结论转写为 Baseline 核心规则时，必须剥离决策过程元数据（选项标识如"选项A/B/C"、方案对比引用、问题编号引用等），只保留最终确认的规则描述；所有已确认的细节规则、字段定义、流程约束、接口参数必须完整保留，不得简化或省略已明确的结论
- **全量覆盖校验**：生成 Baseline 前必须校验分析报告中所有已确认的结论、字段定义、流程规则、接口定义、前端页面信息均已完整映射到 Baseline 对应章节，不得遗漏。仅分析过程元数据、候选方案对比、未确认问题可排除。

#### Baseline 文档结构

按 templates/baseline-structure.md 模板结构输出

#### Baseline 确认

生成后与用户确认 Baseline 内容（交互模式）/ 自动完成（非交互模式），用户确认无误后：
1. 告知用户 Baseline 已完成
2. 告知 Baseline 文件位置
3. 将本次更新详情 Write 到 `变更记录/baseline-v1.md`（遵循 pm-conventions §3.3）
4. 输出知识上下文文件（见下方）

#### 知识上下文文件输出

> 详细规则见 `templates/knowledge-context-rules.md`，包含补全粒度标准、involves_frontend 判定、输出结构等。
