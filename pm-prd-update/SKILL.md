## 运行模式检测

本 skill 支持两种运行模式，通过 prompt 中的标记判断：

| 模式 | 检测方式 | 确认点行为 |
|------|---------|-----------|
| 非交互模式 | prompt 中包含 `[NON_INTERACTIVE]` 标记 | **所有确认检查点自动跳过**，直接执行后续步骤，最终产出物正常生成 |
| 交互模式 | prompt 中不包含 `[NON_INTERACTIVE]` 标记 | 按 agent.json 中 confirmations 配置的 mode 执行：`auto_pass`=自动通过，`user`=根据 agent.json 确认点模式执行 |

**非交互模式下的特殊处理**：
- 变更理解摘要、优化建议等在对话中输出但不等待确认
- 细节确认环节自动通过，未确认细节标记为"待确认（非交互模式）"
- Baseline 更新计划自动通过，直接执行更新
- 最终产出物正常生成

## Purpose

PRD 不是一次写完就结束的。每次迭代都需要：生成修改建议 → 更新 Baseline → 输出新版需求定稿。

这个 skill 将"已有 PRD 的迭代更新"整合为三个阶段的闭环：

1. **Phase 1：生成修改建议** — 识别更新点、评估合理性、确认细节、输出修改建议（支持多轮）
2. **Phase 2：更新 Baseline** — 输出更新计划、确认后生成完整的新版 Baseline
3. **Phase 3：生成需求定稿** — 更新 PRD、执行评审、完成 Baseline 位置映射

用户可以只执行 Phase 1（仅生成修改建议），也可以按需继续 Phase 2、Phase 3 完成完整迭代。

> **与 pm-proto-gen 的分工**：如更新涉及原型变更，完成本 skill 后执行 `/pm-proto-gen` 更新原型。

## 输入

### Phase 1 输入
- **待修改需求稿**（必须）：已有的 PRD 文件路径
- **需更新内容**（必须）：用户描述的修改内容
- **AI 知识库**（如有）：按 pm-conventions §10 读取，在 Phase 1 评估变更可行性时使用

### Phase 2 输入
- **修改建议**（必须）：`sessions/modification-suggestions.json` 中的持久化数据（或对话上下文中的确认建议）
- **待更新 Baseline 文档**（必须）：现有 Baseline 文件路径

### Phase 3 输入
- **修改建议**、**Baseline 文档**、**待修改需求稿**（必须）

## 输出目录规范

```
Developer/my-project/产品需求/{需求名}/
├── 修改建议/                                    # 按需生成（用户要求保存时才创建）
│   └── {需求标题}-修改建议-{版本}.md
├── {需求简称}-Baseline.md                    ← Phase 2 更新（原地修改）
├── 需求文档/
│   └── {需求简称}-需求文档-v{N}.md            ← Phase 3 产出
└── sessions/
    └── {request_id}/
        ├── modification-suggestions.json     ← Phase 1 持久化
        ├── update_change_list.json           ← 变更执行清单
        ├── update_confirmed_sections.json    ← 已确认的更新内容
        └── update_confirmation_log.md        ← 确认过程记录
```

## Phase 间衔接规则

每个 Phase 开始前，AI 必须执行状态检查：

| 当前 Phase | 检查项 | 不存在时处理 |
|-----------|--------|-------------|
| Phase 1 | 待修改需求稿路径是否有效、需更新内容是否已提供 | 提示用户提供 |
| Phase 2 | 修改建议（sessions 或对话上下文）和 Baseline 文件是否存在 | 提示前置步骤 |
| Phase 3 | 修改建议和 Baseline 文件是否存在 | 提示对应前置步骤 |

**需求名称确认**：每个 Phase 开始时，AI 应从文件路径自动推断当前需求名称；如无法推断，主动询问。

## Phase 0：状态检查（自动执行）

> [必须] 从文件路径读取所有输入文件，详见 pm-conventions §5。

按 pm-conventions §5.4 规则扫描需求文件夹。如检测到未完成的变更执行清单或 sessions，告知用户"检测到上次在 Phase X 中断，从中断点继续"并自动恢复。仅当无法判断中断点时才询问用户。

## Phase 1：生成修改建议

> [必须] 从文件路径读取所有输入文件，详见 pm-conventions §5。

> 本阶段支持**多轮执行**。用户每次提出新的变更需求后，可重复执行 Phase 1。每轮修改建议是**独立的增量**，持久化到 sessions，后续 Phase 2/3 综合处理。

### Step 1：识别更新点

根据用户提供的修改内容，识别文档需要更新的点：

1. **读取待修改需求稿**、知识上下文文件（如存在，按 pm-conventions §10.4）和知识库，建立对现有需求的完整理解
2. **解析修改内容**：明确哪些功能/模块受影响
3. **开发边界分析**：特别关注修改是否跨越多个开发团队的边界，明确每个变更归属哪个团队
4. **输出理解摘要**：

📋 **变更理解摘要**

| 修改点 | 影响模块 | 影响团队 | 修改类型 |
|--------|---------|---------|---------|
| {修改点 1} | F-XX {功能名} | {团队} | 功能新增/逻辑修改/... |

用户确认理解无误后，进入 Step 2。（非交互模式下自动通过，直接进入 Step 2）

### 通用能力变更的级联影响分析

当修改涉及通用能力时：

1. 读取 Baseline 的能力引用矩阵
2. 列出所有引用该能力的业务场景，区分"完全复用"和"差异复用"
3. 在修改建议中增加"级联影响"章节

### Step 2：合理性评估与优化建议

将修改内容与已有需求文档内容**结合起来**，整体评估：

1. **修改内容自身合理性**：逻辑是否自洽？是否有遗漏场景？
2. **与已有内容的一致性**：是否与其他已确认功能存在矛盾？
3. **影响范围评估**：是否连带影响其他模块？
4. **与 Baseline 的一致性**：是否与已确认规则冲突？
5. **优化建议**：综合已有需求全貌，是否有更优方案？
6. **与用户沟通确认**（交互模式）/ **自动通过**（非交互模式：AI 自行评估合理性，有风险时标注"待确认"）

### Step 3：细节确认

结合修改内容与已有需求文档，识别未确认细节（边界条件、异常处理、权限变更等）。
- **交互模式**：如有未确认细节，逐一与用户确认。
- **非交互模式**：识别未确认细节后，AI 基于已有信息推断并标注"待确认（非交互模式）"，自动通过。

**无变更快速路径**：如评估后无需调整且无遗漏细节，可合并 Step 2/3 快速完成。

### Step 4：输出修改建议

在对话中输出【确认后修改建议】，格式遵循 pm-conventions §7 修改建议统一格式。

**不生成独立 .md 文件**——修改建议在对话中展示，用户确认后直接作为 Phase 2/3 的输入。

**持久化到 sessions/**：用户确认后，将建议内容写入 `sessions/modification-suggestions.json`，确保会话中断后可恢复。JSON 字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| version | string | 建议生成时间戳 |
| items | array | 变更项列表，每项含 target_section / change_type / description / confirmed |
| baseline_impact | array | 需同步更新的 Baseline 条目 |

> **例外**：如果用户明确要求"保存修改建议为文档"，才额外生成 .md 文件保存到 `修改建议/` 目录。

> **约束**：此环节不可更新已有需求文档。修改建议确认后，在 Phase 2/3 中统一更新。

## Phase 2：更新 Baseline

> **状态检查**：开始前确认修改建议和 Baseline 文件均存在。

> [必须] 从文件路径读取所有输入文件，详见 pm-conventions §5。

### Step 1：输出更新计划

根据已确认的修改建议（如有多轮，综合所有），输出 Baseline 更新计划：

1. 对比修改建议与现有 Baseline 中的确认点
2. 列出需要**新增**、**修改**、**删除**的 Baseline 规则
3. 与用户确认更新计划（交互模式）/ **自动通过**（非交互模式：AI 自行判断更新计划，直接执行 Step 2）

**无变更快速路径**：如修改建议不影响 Baseline 核心规则，告知用户"Baseline 无需更新"并跳过 Step 2。

### Step 2：更新 Baseline 文档

确认后，在**原 Baseline 文件上直接修改**。更新操作规则遵循 pm-conventions §3.3。

#### 知识上下文同步检查

Baseline 更新完成后，检查知识上下文文件是否需要同步：

| Baseline 更新类型 | 知识上下文同步动作 |
|:-----------------|:----------------|
| 新增模块（功能架构变更） | 检查知识上下文文件是否包含新模块涉及服务的信息，缺失时按 §10.4 补读知识库并追加到知识上下文文件 |
| 修改已有模块的核心规则 | 不同步（知识上下文记录的是系统现状，非需求规则） |
| 删除模块 | 不同步（知识上下文信息仍可能对其他模块有参考价值） |

> 同步后更新知识上下文文件的"最后更新"时间戳。

## Phase 3：生成需求定稿

> **状态检查**：开始前确认修改建议、Baseline 文件、待修改需求稿均存在。

> [必须] 从文件路径读取所有输入文件，详见 pm-conventions §5。

### Step 1：更新需求文档

根据【需更新内容】与【最新 Baseline】，基于【待修改需求稿】生成新版本需求文档。

> **版本管理铁律**：必须创建新版本文件（版本号 +1），**禁止原地修改**。详见 pm-conventions §3。

#### 更新前准备

读取 `pm-conventions/templates/change-execution.md`，按其中的规则执行：

1. 生成变更执行清单
2. 连带影响扫描（结合 Baseline 位置映射表）
3. 用户确认完整清单（交互模式）/ **自动通过**（非交互模式：AI 自行验证清单完整性，直接执行更新）
4. 根据文档行数选择更新策略

#### 更新内容确认

按 `templates/change-execution.md` 中的确认规则，批量输出更新内容供用户确认。确认结果写入 sessions 目录。

#### 执行更新

按确认内容统一修改文档。以 sessions 目录中 `update_confirmed_sections.json` 的确认内容为准。

#### 更新规则

**通用写作规则**：遵循 pm-prd-draft Phase 2 中的文档生成原则（产品语言、单点描述、交互说明条件化、可测性标准、流程图规范等）和 pm-conventions §6 格式规范。

**更新特有规则**：
- 如 Baseline 有发生变更，务必保证所有关联位置的需求文档都进行更新
- 所有正式需求描述中不要体现历史版本信息
- 如待修改需求稿含 YAML frontmatter，同步更新 `version` 字段
- 更新文档开头【版本记录】，仅需简述版本更新信息
- 文档末尾记录详细【更新记录】

#### 更新后自检

按 `templates/change-execution.md` 中的自检规则执行，输出执行结果对照表。

### Step 2：后续提示

更新后自检通过后，输出以下提示并终止流程：

> ✅ 需求文档已更新：`{文件路径}`（v{N}）
>
> ⚠️ **请结束当前会话，在新会话中执行评审。** prd-review 使用 Sonnet 模型即可，无需 Opus。
> ```
> claude --model sonnet
> /pm-prd-review {需求名}
> ```

### 流程结束声明

> 详见 pm-conventions §11。提示输出后流程终止，后续修改通过 `pm-prd-update` 新一轮执行。
