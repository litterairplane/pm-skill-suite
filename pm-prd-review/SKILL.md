## 运行模式检测

本 skill 支持两种运行模式，通过 prompt 中的标记判断：

| 模式 | 检测方式 | 确认点行为 |
|------|---------|-----------|
| 非交互模式 | prompt 中包含 `[NON_INTERACTIVE]` 标记 | **所有确认检查点自动跳过**，直接执行后续步骤，最终产出物正常生成 |
| 交互模式 | prompt 中不包含 `[NON_INTERACTIVE]` 标记 | 按 agent.json 中 confirmations 配置的 mode 执行：`auto_pass`=自动通过，`user`=根据 agent.json 确认点模式执行 |

**非交互模式下的特殊处理**：
- 评审发现的阻塞问题（🔴）自动批量修复（上限 3 轮）
- 建议问题（🟡）自动采纳 AI 建议
- 提示问题（🔵）仅通知
- 修复方案不等待用户确认，直接执行

## 角色锚定

执行本 skill 时，AI 以**资深需求评审官**身份工作：聚焦文档完整性和自洽性，以"开发拿到这份文档能否无歧义地开工"为核心判断标准。不替作者美化文档，不降低标准放水，也不吹毛求疵地制造噪音。

## Purpose

PRD 生成或更新后的质量验证闭环。逐项校验 Baseline 覆盖性，执行结构性评审，调用 `pm-baseline-mapping` 完成位置映射。

**定位**：轻量结构性检查，不加载知识库，不做知识库交叉校验。

## 运行建议

本 skill 推荐使用 Sonnet 模型执行。交互模式下使用 `claude --model sonnet` 启动会话。

## 输入

- **Baseline 文档**（必须）：自动从需求目录发现
- **需求文档**（必须）：自动从需求目录发现最新版本
- 用户也可手动指定文件路径

## 工作流程

### Phase 0：自动发现文件（静默执行）

1. 根据用户提供的信息或当前上下文，定位需求目录
2. 扫描目录，自动发现 `*-Baseline.md` 和 `需求文档/*-需求文档-v*.md`
3. 如有多个需求文档版本，使用最新版本（按版本号排序）
4. 输出状态摘要：

> ✅ 已定位文件
> - Baseline：`{路径}`
> - 需求文档：`{路径}`（v{N}）

如无法定位，提示用户提供路径。

### Phase 1：Baseline 覆盖性校验

> [必须] 从文件路径读取所有输入文件，详见 pm-conventions §5。

逐项检查 Baseline 中的每个确认点**是否在需求文档中存在对应描述**（覆盖性检查）。

1. 逐项检查 Baseline 中的每个能力/功能是否在需求文档中有对应描述
2. 如有能力引用矩阵，逐项检查引用关系是否正确体现
3. 输出覆盖性报告：

| 状态 | Baseline 确认点 | 需求文档对应位置 |
|------|----------------|----------------|
| ✅ 已覆盖 | {确认点} | {位置} |
| ❌ 缺失 | {确认点} | — |

4. 缺失项需补充后重新校验直到全部覆盖

### Phase 2：轻量结构性评审

**文件读取隔离要求**：评审前必须从文件路径重新读取需求文档，避免确认偏误。

**与 Phase 1 的分工**：Phase 1 检查"存在性"（每条 Baseline 确认点在 PRD 中是否有对应），Phase 2 检查"质量"（已存在的描述是否完整、自洽、可交付）。Phase 1 已确认覆盖的条目，Phase 2 不重复检查存在性，仅检查内容质量。

**特别注意跨模块一致性**——功能清单与需求详情的对应关系、流程图角色与需求详情的一致性。

#### 2.1 快速扫描（一轮完成）

对以下维度做快速扫描，仅记录发现的问题，不逐项展开：
- 需求背景是否有依据、范围是否界定
- 功能清单与需求详情是否对应完整
- 业务流程图主流程完整性、判断分支规则与需求详情是否一致
- 需求详情的交互说明、约束条件、边界条件、错误处理是否可验收
- 功能架构组织（通用能力层完整描述、业务场景层正确引用）

> 发现问题时记录并标注严重程度，不在本步骤展开修复讨论。

#### 2.2 可测性轻量预检

- **禁止模糊词**：不得出现"尽快""适当""较好""用户友好""合理"等，发现标 🟡 并给出替换写法
- **流程图分支完整**：每个判断节点必须有判断条件和分支走向，缺失标 🔴
- **文档内部无逻辑矛盾**：以 Baseline 功能架构树中的功能模块为锚点，检查同一功能在 PRD 不同章节中的描述是否一致（如功能清单描述 vs 需求详情描述 vs 流程图节点），发现矛盾标 🔴。如 Baseline 无功能架构树，以功能清单中的模块划分为锚点

> 深度可测性评审请使用 `testability-api-client` skill。

#### 2.3 Baseline 一致性

**Baseline → PRD**：逐条检查确认结论在 PRD 中的描述是否与 Baseline 一致（矛盾→🔴，不够详细→🟡）

**PRD → Baseline**：识别 PRD 中的重要规则，Baseline 未覆盖→🟡

**能力引用矩阵覆盖性检查**：矩阵中每个通用能力和引用关系在 PRD 中有对应

问题严重程度定义详见 pm-conventions §4。

#### 评审结果处理

**评审结果分级处理**：
- **交互模式**：阻塞问题（🔴）必须修复；建议问题（🟡）与用户确认；提示问题（🔵）仅通知
- **非交互模式**：阻塞问题（🔴）自动修复；建议问题（🟡）自动采纳 AI 建议；提示问题（🔵）仅通知

**🔴 阻塞问题批量修复**：
1. 评审发现阻塞问题 → **批量生成所有阻塞问题的修复方案**
2. 一次性输出全部修复内容（修复前后对比）
3. **交互模式**：供用户统一确认，用户可逐条确认或批量确认，仅对有异议的修复单独讨论
4. **非交互模式**：修复方案自动通过，直接执行修复
5. 确认后（非交互模式自动确认）统一更新需求文档
5. 从文件路径重新读取，重新评审，直到阻塞问题清零
6. 最多自动修复 3 轮；单次批量修复上限 5 个
7. **达到上限后处理**：

> **问题粒度定义**：按评审意见输出中的行数计算，每行（每条独立的问题描述）算一个问题。同一模块内的多个子问题分别计数。
   - 自动修复 3 轮后仍有阻塞问题 → 输出剩余未修复问题清单，告知用户"以下阻塞问题超出自动修复能力，建议通过 pm-prd-update 手动处理"
   - 单次修复数量超过 5 个 → 优先修复严重程度最高的 5 个，剩余问题列入下轮修复或引导用户处理

**修复范围限定**：修复仅限结构性补充（如补缺失的异常分支、修正编号错误、补充缺失的约束条件等）。涉及业务逻辑变更的修复应通过 `pm-prd-update` 执行，本 skill 仅标记问题不代行修复。

**Baseline 回退路径**：遵循 pm-conventions §3.3 Baseline 局部修复规则。
- 仅涉及 1-2 条确认点 → 在本 skill 内直接修复 Baseline
- 涉及 3 条及以上 → 提示用户通过 `pm-prd-update` 更新 Baseline 后重跑本 skill

### Phase 3：位置映射与总结（静默执行后一次性输出）

评审通过后，自动执行以下步骤，**不需要用户逐步确认**：

1. 调用 `pm-baseline-mapping` 完成位置映射
2. 生成评审报告文件到 `评审报告/` 目录，文件名格式：`{需求标题}-v{N}-需求评审报告.md`（N 为本次评审的需求文档版本号）。评审报告内容包括：覆盖性校验结果、结构性评审结果概要、修复记录（如有）、位置映射完成状态
3. 一次性输出最终总结：
   - Baseline 文件位置
   - 需求文档文件位置和版本
   - 评审报告文件位置
   - Baseline 覆盖性校验结果（覆盖率）
   - 结构性评审结果概要
   - Baseline 位置映射完成状态
   - 建议下一步：迭代修改用 `pm-prd-update`

**总结详细度自适应**：≤ 3 模块精简总结（文件位置+关键结论），> 3 模块完整总结。

### 流程结束声明

> 详见 pm-conventions §11。总结输出后流程终止，后续修改通过 `pm-prd-update` 执行。
