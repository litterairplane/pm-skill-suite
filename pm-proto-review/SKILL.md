## 运行模式检测

本 skill 支持两种运行模式，通过 prompt 中的标记判断：

| 模式 | 检测方式 | 确认点行为 |
|------|---------|-----------|
| 非交互模式 | prompt 中包含 `[NON_INTERACTIVE]` 标记 | **所有确认检查点自动跳过**，直接执行后续步骤，最终产出物正常生成 |
| 交互模式 | prompt 中不包含 `[NON_INTERACTIVE]` 标记 | 按 agent.json 中 confirmations 配置的 mode 执行：`auto_pass`=自动通过，`user`=根据 agent.json 确认点模式执行 |

**非交互模式下的特殊处理**：
- 评审意见自动确认，直接执行更新
- Baseline 和原型更新自动执行
- 最终产出物正常生成

---

## Purpose

基于 Baseline + 原型的交互评审 skill。从交互设计视角检查原型的交互完整性和合理性，输出评审意见，引导更新 Baseline 和原型。

> **核心约束**：本 skill 使用 Sonnet 执行，其 Baseline 更新范围**仅限交互层面**（操作反馈方式、UI 行为、布局调整等）。涉及业务逻辑的问题不在本 skill 内修改 Baseline，而是标记为"需 pm-prd-update 处理"，由 Opus 在后续流程中处理。

## 输入

- **Baseline 文档**（必须）：`{需求简称}-Baseline.md`
- **原型 HTML 文件**（必须）：`原型/` 目录下的 HTML 文件

## 输出

- 更新后的 Baseline 文档（原地修改）
- 更新后的原型 HTML 文件
- 评审意见（保存到 `修改建议/` 目录）

## Phase 0：状态检查

`[Phase 0 · 状态检查]`

1. 验证 Baseline 和原型文件存在
2. 读取已有评审记录（如有）
3. **中断恢复**：参照 pm-conventions §5.2 规则扫描已有产物判断执行状态

| 检测结果 | 恢复入口 |
|---------|---------|
| 无评审产物 | 从 Phase 1 开始 |
| 有评审意见但未确认 | 从 Phase 2 Step 1 开始（确认评审意见） |
| 评审意见已确认，Baseline 已更新但原型未更新 | 从 Phase 2 Step 3 开始（更新原型） |
| 评审意见已确认，Baseline 和原型均已更新 | 告知用户已完成，询问是否需要新一轮评审 |

4. **原型来源判断**：通过 `<!-- proto-banner: exploratory/precise -->` 标记判断原型类型
   - 探索性原型 → 正常评审流程
   - 精确原型 → 告知用户："当前为精确原型（基于 PRD 生成），评审发现的问题将标记为需通过 pm-prd-update 处理"，后续引导按「流程终止与后续引导」章节的精确原型分支执行

## Phase 1：交互评审

> [必须] 从文件路径读取所有输入文件，详见 pm-conventions §5。

### Step 1：交互设计评估

`[Phase 1 · Step 1/2]`

基于 Baseline + 原型 HTML，从交互设计视角检查核心业务功能的**交互完整性和合理性**。

**评审严格度根据原型来源自动适配**：

| 评审维度 | 探索性原型（Baseline 模式产出） | 精确原型（PRD 模式产出） |
|---------|------|------|
| 评审目标 | 方向验证：功能覆盖 + 核心流程可走通 | 交付验收：字段、规则、状态完全对齐 |
| 硬约束 | 仅检查"操作反馈"和"状态可感知性" | 完整硬约束清单（操作反馈/异常提示/状态可感知性） |
| 软指标 | 仅关注"操作路径"和"信息架构" | 完整软指标清单 |
| 缺失项处理 | 标记为"待 PRD 补充"，不判定为"不通过" | 判定为"不通过"并要求修复 |

**原型来源判定**：通过 HTML 注释标记判断原型来源：
- `<!-- proto-banner: exploratory -->` → 探索性原型（Baseline 模式产出）
- `<!-- proto-banner: precise -->` → 精确原型（PRD 模式产出）
- 无标记 → 按探索性原型处理（兼容旧版原型）

**硬约束检查清单**：

| 检查项 | 判定标准 | 不通过时 |
|--------|---------|---------|
| 操作反馈 | 每个写操作是否说明了成功/失败的用户反馈方式 | 标记为必须补充项 |
| 异常提示 | 异常场景的提示文案是否具体可操作 | 标记为必须补充项 |
| 状态可感知性 | 多步/异步操作中用户能否感知进度和下一步 | 标记为必须补充项 |

**软指标检查清单**：

| 检查项 | 参考标准 |
|--------|---------|
| 操作路径 | 标记超过 5 次点击的路径 |
| 信息架构 | 重要信息是否优先展示 |
| 一致性 | 与现有系统交互模式是否一致 |
| 权限控制 | 不同角色的页面元素可见性/可操作性是否说明 |

**整体评审结论判定**：
- ✅ 通过：当前原型类型适用的所有硬约束检查通过（探索性原型适用 2 项，精确原型适用 3 项，详见评审严格度表格）
- ❌ 不通过：任一适用硬约束未通过
- 软指标不影响通过/不通过判定，仅作为优化建议输出

**输出**：通过/不通过汇总 + 不通过项清单（仅对不通过项展开详细分析）

### Step 2：输出评审意见

`[Phase 1 · Step 2/2]`

根据 Step 1 确认结果，生成评审意见文档，格式遵循 pm-conventions §7，来源类型标注为"交互评审"。

每条意见标注影响目标：Baseline / 原型 / 两者 / 标记待处理。

保存到 `修改建议/` 目录。

## Phase 2：确认与更新

### Step 1：用户确认评审意见

`[Phase 2 · Step 1/3]`

- **交互模式**：支持批量确认或逐条调整；用户查看原型后可补充新发现
- **非交互模式**：评审意见自动通过，直接进入 Step 2（更新 Baseline）

### Step 2：更新 Baseline

`[Phase 2 · Step 2/3]`

对比评审意见与 Baseline 确认点，识别需调整的规则。

**无变更快速路径**：Baseline 无需调整时直接跳过。

在原 Baseline 文件上直接修改（遵循 pm-conventions §3.3）。

### 评审意见的分流规则

| 评审意见类型 | 示例 | 更新目标 | 处理方式 | 复杂度判定 |
|------------|------|---------|---------|-----------|
| 交互方案调整 | "搜索栏改为默认折叠" | 仅原型 | 本 skill 内直接处理 | 纯交互 |
| 数据展示优化 | "表格列顺序调整" | 仅原型 | 本 skill 内直接处理 | 纯交互 |
| 交互反馈补充 | "批量操作需要二次确认弹窗" | Baseline（交互层）+ 原型 | Baseline 新增交互类确认结论 + 原型添加确认弹窗 | 纯交互 |
| UI 元素补充 | "列表页缺少筛选条件""表格缺少操作列" | Baseline（交互层）+ 原型 | Baseline 补充 UI 元素 + 原型添加对应组件 | 纯交互 |
| 功能逻辑新增 | "列表页缺少导出功能（含数据筛选/格式选择）" | 标记待处理 | **不在本 skill 处理**，生成待处理建议标记"需 pm-prd-update 处理" | 涉及业务逻辑 |
| 流程/业务逻辑完善 | "异步操作缺少失败重试机制" | 标记待处理 | **不在本 skill 处理**，生成待处理建议标记"需 pm-prd-update 处理" | 涉及业务逻辑 |
| 业务规则变更 | "审批层级需要从两级改为三级" | 标记待处理 | **不在本 skill 处理**，同上 | 涉及业务逻辑 |

> **UI 元素补充 vs 功能逻辑新增的判定标准**：
> - UI 元素补充：仅涉及页面可见元素的增减（按钮、筛选条件、表格列等），不引入新的业务逻辑或后端接口需求
> - 功能逻辑新增：虽然表现为 UI 元素缺失，但背后隐含新的业务逻辑（如导出需要数据查询+格式转换、批量操作需要后端批处理接口）
> - 判断不确定时，按「功能逻辑新增」处理，标记待 pm-prd-update 处理

### Step 3：更新原型

`[Phase 2 · Step 3/3]`

根据确认的评审意见修改原型 HTML。

> 原型更新遵循 pm-proto-gen `templates/generation-rules.md` §原型迭代步骤（`<!-- anchor: proto-iteration-steps -->`）。

**无变更快速路径**：原型无需调整时直接跳过。
